# 사내 BI 플랫폼

상담 기반 법률 서비스의 데이터를 모아 **경영·운영 판단에 쓰는 BI 플랫폼**입니다.
지표를 보여 주는 데서 끝나지 않고, **이번 달 얼마가 들어올지 예측**하고, **평소와 다른 지표를 먼저 띄우고 왜 움직였는지 원 단위로 쪼개고**,
**기존 의뢰인에게 필요할 법한 다음 사건을 추천**하는 것까지가 범위입니다.

> 실무에서 기획·개발·운영한 사내 BI 플랫폼의 핵심 로직을 **합성 데이터로 다시 구현한 공개본**입니다.
> 회사 코드·데이터는 포함되어 있지 않으며, 인물·사건·금액은 전부 시드 고정 난수로 만든 것입니다.

```
Python · FastAPI · SQLite(읽기 전용) · React 19 · TypeScript · Vite · Tailwind · Recharts
```

## ① 당월 매출 예측

경영진은 매일 "이번 달 온라인 신규 사건 입금이 월말에 얼마가 되고, 목표의 몇 %인가"를 봅니다.
원래 메신저로 나가던 일일 리포트 스크립트의 계산을 화면으로 옮겼습니다.

```
월말 예상 F = 확정 입금 + 추심 예정 + 신규 유입          달성률 = F / 월 목표 × 100

추심 예정 = Σ 미납 회차 금액 × P(연체일수)              P = 0.8 (0일) · 0.1 (1~10일) · 0 (10일 초과 또는 90일 무납부)
신규 유입 = Σ(남은 날 요일별 평균 계약 수 × 공휴일 0.5) × 최근 28일 평균 약정금 × 계약 당일 지급률
```

- **학습 모델 대신 설명 가능한 산식.** 현업이 "왜 이 숫자인가"를 물으면 카드의 세 항목과 곱셈 하나로 답할 수 있어야 합니다.
- **환불은 음수 라인.** 그 달 확정 입금의 일부지만, 추심 예정과 지급률 계산에서는 빼서 미래 추정을 오염시키지 않습니다.
- **최근 28일.** 요일을 4번씩 포함하는 가장 짧은 창이라 요일 편차를 살리면서 최근 추세를 따라갑니다.
- **미수금 예상액을 함께 노출.** "예측이 낮다"보다 **"회수하러 가야 할 금액"**이 바로 행동으로 이어졌습니다.
- **성공보수는 별도 추정** ([`success_fee.py`](backend/app/services/success_fee.py)). 종결일 코호트를 쓰면 우측 절단으로 확률이 낮게 나와 쓰지 않고, 표본 20건 미만 조합은 상위 분류로 올라갑니다. 수령비율 분모는 발생한 건만 씁니다(전체를 쓰면 발생확률이 두 번 곱해짐).

**과거 시점 백테스트** (매월 15일에 예측 → 그 달 실제 확정 입금과 비교, `GET /api/forecast/backtest`)

## ② 별건 추천

한 수임 안에 사건이 여러 개인 경우가 매출 단위입니다(이혼 → 재산분할·양육권, 형사 → 손해배상).
성격이 다른 세 갈래로 돌아가며, **통계로 충분한 곳에는 모델을 쓰지 않습니다.**

| 갈래 | 방식 | 공개본 |
|---|---|---|
| A. 동시출현 | 수임 = 장바구니, P(b\|a) = 함께 선임 / a 선임, **동시출현 2건 미만은 버림** | 구현 |
| B. 근거 콘텐츠 | 질의 = 추천 유형명 + 상담 내용. 정렬은 유사도, 키워드 겹침은 "왜 이 사례인가"의 근거로만 | 운영은 BM25 + 임베딩 kNN, 공개본은 글자 2-gram TF-IDF로 대체 |
| C. 원문 별건 단서 | LLM 추출 → 독립성 검증 → 분류 확정, 10분 주기 배치 | 모델 호출은 제외, **출력 검증 규칙만** 구현 ([`leads.py`](backend/app/services/leads.py)) |

- **빈 칸보다 넓힌 추천.** 소분류에 사례가 없으면 대분류·전체로 넓히되 비매칭 표시를 남깁니다.
- **LLM이 값을 지어내지 못하게.** 인용은 원문에 그대로 있어야 하고, 분류는 목록에 있는 ID만 받습니다. 응답 형식이 깨지면 "후보 없음"으로 넘기지 않고 재시도합니다. 놓친 것과 없는 것을 구분하기 위해서입니다.
- **발송은 사람이.** 화면은 "전송 등록"만 열고, 발송 직전 마케팅 동의를 다시 조회합니다.

## ③ 플랫폼 구조

- **읽기 전용 원천.** 운영 DB를 직접 건드리지 않고, 매일 복제되는 읽기 전용 사본을 화면 요청마다 읽습니다. 화면 요청에서는 외부 모델을 부르지 않습니다.
- **단일 스냅샷 조회.** 지표마다 원본을 따로 읽으면, 조회 도중 들어온 신규 건이 어떤 지표에만 잡혀 **같은 날 숫자가 조회마다 1건씩 달랐습니다.** 한 번만 읽고 그 스냅샷으로 모든 지표를 셉니다.
- **흩어진 날짜 조회.** 같은 요일 12주처럼 띄엄띄엄한 날짜는 `IN` 옆에 결과를 바꾸지 않는 범위 조건을 붙여 인덱스를 탈 여지를 만듭니다 ([`db.py`](backend/app/db.py)).
- **기본 거부 권한.** 모든 라우트는 메뉴 권한·로그인·공개 중 하나를 선언해야 하고, **선언 없는 라우트가 있으면 서버가 뜨지 않습니다.** 메뉴 정의는 프런트의 사이드바 파일([`menu.json`](frontend/src/menu.json)) 하나를 서버가 직접 읽습니다.
- **실패를 허용으로 처리하지 않음.** 권한 표를 못 읽으면 빈 목록, 프런트는 홈만 엽니다. 그룹 키가 리프 키와 같아 메뉴 하나만 허용해도 다른 화면이 열리던 문제를 막습니다.
- **캐시 수명.** 조회 스냅샷 30초, 사례·메타 5분, 동시출현 집계 10분. 사용자 권한은 캐시하지 않습니다.

## ④ 경영 모니터링 · 원인 분해

```
z = |x − μ| / σ          Δ = |x − μ| (비율, %p)  또는  |x − μ| / μ × 100 (건수·금액, %)
score = max(z / 1.5, Δ / θ),   θ = 30% 또는 10%p,   score ≥ 1 이고 기준 대비 10% 이상이면 후보 → 상위 3개만
```

- **비교 기준.** 일간은 같은 요일 직전 12주, 주간은 직전 12개 ISO 주, 월간은 직전 3개월입니다.
- **z만 쓰지 않는다.** 변화율만으로 줄 세우면 원래 출렁이는 지표가 늘 1등이 되고, z만 쓰면 출렁이는 지표가 30~40% 빠져도 안 뜹니다.
- **알림은 3개까지.** 매일 많이 뜨면 아무도 보지 않습니다.

**합이 정확히 맞는 원인 분해** — "왜?"를 누르면 선임형태·약정금 구간·상담유형·사건 분류·유입경로·상담변호사별 기여도를 보여 줍니다.

```
부가가치  A₁/N₁ − A₀/N₀ = (A₁−A₀)/N₁ + A₀(N₀−N₁)/(N₁N₀)          금액 효과 + 건수 효과
기여도    cᵢ = sᵢ¹vᵢ¹ − sᵢ⁰vᵢ⁰,   Σ cᵢ = 전체 차이                    "이 유형이 평균을 몇 원 끌어내렸나"
선임률    각 행 = 구성 효과 (wᵢ¹−wᵢ⁰)((rᵢ¹+rᵢ⁰)/2 − R̄) + 전환 효과
```

- **R̄(전체 평균)를 빼는 이유.** 빼지 않으면 선임률이 0보다 크기만 해도 비중이 늘어난 행은 무조건 양(+)으로 읽혀, **평균보다 못한 집단의 비중 증가가 "긍정 기여"로 보고됩니다.** 비중 변화의 합이 0이라 총합은 그대로입니다.
- **기준은 기간 합산.** 단순 평균이 아니라 기준 기간을 통째로 합산해야 기여도 합이 원 단위로 맞습니다. 카드 기준값과 다를 수 있어 응답에 둘 다 싣습니다.
- **노이즈 차단.** 변호사처럼 사람 단위 차원은 표본 3건 미만을 "기타"로 묶습니다(합계 보존). 상위 3개 설명력이 낮으면 "특별한 원인 없음"으로 표시합니다.
- **공식 수치는 바꾸지 않는다.** 자문·저액 제외는 기본값을 바꾸지 않고 토글로만 두고, 켜면 "공식 수치와 다름"을 표시합니다.

## 운영에서 겪은 사고와 공개본의 대응

| 증상 | 원인 | 대응 |
|---|---|---|
| 같은 날 선임 건수가 조회마다 1건씩 달랐다 | 지표별 쿼리가 라이브 원본을 각자 다시 읽었다 | 단일 스냅샷 조회 |
| 출렁이는 지표가 30% 넘게 빠졌는데 안 떴다 | z가 문턱 아래였다 | z와 변화폭을 각자 문턱으로 정규화 |
| 하루 부가가치가 급락했다 | 약정금 없이 성공보수만 약정한 건이 일괄 등록돼 분모만 늘었다 | 드릴다운으로 특정, 저액 제외 토글 (합성 데이터 2026-04-14에 재현) |
| 월간 "왜?"의 기준값이 카드와 어긋났다 | 카드와 분해가 다른 기간 수를 썼다 | 같은 상수를 쓰고 두 기준값을 함께 표시 |
| 확정 입금이 회계보다 커 보였다 | 사임 환불을 집계에서 뺐다 | 환불을 음수 라인으로 |
| 권한 표를 못 읽자 모든 메뉴가 열렸다 | 실패를 허용으로 처리했다 | 서버는 빈 목록, 프런트는 홈만 |
| 라벨마다 같은 영상이 추천됐다 | 영상에 유형 메타데이터가 없다 | 라벨마다 한 건, 아직 안 쓴 영상만 |

운영 코드 검토에서 남은 과제로 기록돼 있던 두 가지는 공개본에서 고쳤습니다.
- 오늘 들어온 착수금이 확정 입금과 신규 유입에 이중으로 들어갈 수 있었다 → 신규 유입은 **내일부터** 셉니다.
- 계약이 없던 날이 요일 평균에서 빠져 계약 수가 높게 추정됐다 → **0건인 날도** 평균에 넣습니다.

공개본을 만들며 새로 찾은 것도 있습니다.
- 과거 날짜로 예측을 다시 보면 그 뒤에 들어온 입금이 "이미 납부"로 보여 추심 예정이 0에 가까워졌다 → **기준일 시점의 미납**으로 판단합니다(백테스트가 가능해진 이유).
- 날짜를 빨리 바꾸면 먼저 보낸 요청의 응답이 늦게 도착해 화면을 덮어썼다 → 지난 요청의 응답은 버립니다.
