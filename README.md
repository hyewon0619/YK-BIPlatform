# 상담 전환 퍼널 BI


콜 → 예약 → 방문 → 계약으로 이어지는 **상담 전환 퍼널**을 분석하는 BI 대시보드입니다.
지표 조회에 그치지 않고, **"어제보다 떨어졌다"를 넘어서 그게 진짜 이상인지 판정**하고
**월 매출을 예측**하는 것까지가 범위입니다.

> 사용된 데이터는 전부 **시드 고정 난수로 생성한 합성 데이터**입니다.
> 실제 조직·고객 정보는 한 건도 포함되어 있지 않습니다.

```
FastAPI + SQLite  ·  React 19 + TypeScript + Vite + Tailwind + Recharts
```

## 무엇을 푸는 프로젝트인가

상담 기반 비즈니스(로펌·병원·학원·딜러십 등)에서 반복되는 세 가지 질문을 다룹니다.

| 질문 | 이 프로젝트의 답 |
|------|------------------|
| 오늘 숫자가 나쁜 건가, 원래 이런 요일인가 | 같은 요일 12주 분포와 비교하는 **robust z-score 이상 탐지** |
| 떨어졌다면 어디가 떨어졌나 | 지점 / 권역 / 채널 / 상담유형 / 이탈사유 **드릴다운** |
| 이번 달 얼마나 나올까 | 과거 진척률 기반 **pacing 매출 예측** + 구간 추정 |

## 핵심 설계 포인트

### 1. 퍼널은 "콜 인입일 코호트"로 묶는다

계약일 기준으로 세면 같은 날의 콜과 계약이 서로 다른 모수라서 전환율이 왜곡됩니다.
그래서 **콜이 인입된 날을 기준으로 그 건이 나중에 어디까지 갔는지**를 추적합니다.

```sql
SELECT COUNT(*)                                            AS calls,
       SUM(CASE WHEN reserved_date IS NOT NULL THEN 1 END) AS reservations,
       SUM(CASE WHEN visit_date    IS NOT NULL THEN 1 END) AS visits,
       SUM(CASE WHEN contract_date IS NOT NULL THEN 1 END) AS contracts
FROM consultation
WHERE call_date BETWEEN :start AND :end
```

### 2. 이상 탐지 — 요일 효과를 먼저 제거한다

콜 물량은 월요일이 일요일의 **4배**입니다. 전일 대비 비교는 매주 월요일마다 "급증"을 냅니다.
그래서 **같은 요일의 과거 12주**를 기준 분포로 삼습니다.

평균·표준편차 대신 **중앙값·MAD**를 씁니다. 기준 구간 안에 이상치가 섞여 있으면
평균과 표준편차가 같이 끌려가서 정작 그 이상치를 못 잡기 때문입니다.

```
robust_z = 0.6745 × (x − median) / MAD
```

**z-score만으로는 오탐이 너무 많았습니다.** 토요일 계약 건수처럼 값 자체가 작은 지표는
한두 건만 흔들려도 MAD가 작아 z가 쉽게 튑니다. 그래서 조건을 셋으로 늘렸습니다.

1. `|robust z| ≥ 3.5`
2. 기준 중앙값 대비 **상대 편차 25% 이상**
3. **지표 2개 이상이 동시에** 이탈 (실제 사고는 여러 지표를 같이 흔든다)

#### 튜닝 근거

데이터 생성기에 **의도적으로 5개 이상 구간을 심어두고** 파라미터를 스윕했습니다.
(광고 계정 중단, 예약 시스템 장애, 연휴 직후 유입 감소, 바이럴 유입 폭증, 상담 인력 이탈)

| z | 상대편차 | 동시 지표 | 적중 구간 | 오탐 | 오탐률 |
|---|---------|----------|----------|------|--------|
| 3.5 | 25% | 1개 | 5/5 | 54 | 8.4% |
| **3.5** | **25%** | **2개** | **5/5** | **15** | **2.3%** ⬅ 채택 |
| 3.5 | 45% | 2개 | 3/5 | 7 | 1.1% |
| 5.0 | 25% | 2개 | 3/5 | 1 | 0.2% |

640일 전체 스캔 기준 **심어둔 5개 구간을 모두 적중**하면서 오탐률 2.3%.

실제 탐지 예시 (2025-11-17, '상담 인력 이탈'을 심어둔 날):

```
   calls               124  (기준 119.0,  4.2% 차, z=0.27)
   reservations         33  (기준  60.5, 45.5% 차, z=-2.85)
   contracts            13  (기준  24.0, 45.8% 차, z=-2.97)
🚩 reservation_rate   26.6  (기준 51.65, 48.5% 차, z=-7.51)
🚩 overall_rate       10.5  (기준  20.5, 48.8% 차, z=-8.43)
→ anomalous: True (2개 동시 이탈)
```

콜 인입은 정상인데 **예약 전환만 무너진** 패턴이라, 유입 문제가 아니라
응대 쪽 문제라는 것까지 읽힙니다.

### 3. 매출 예측 — 설명 가능한 방법을 골랐다

회귀 모델 대신 **pacing(진척률)** 방식을 썼습니다.

```
예측 = 이번 달 D일까지 누적 ÷ median(과거 달들의 D일 진척률)
```

이유:
- 월 길이·요일 배치·계절성이 진척률 안에 **이미 녹아 있다**
- 과거 달이 20개 남짓이라 파라미터 많은 모델은 과적합된다
- **왜 그 숫자가 나왔는지 실무자에게 설명할 수 있다** — BI에서는 이게 정확도만큼 중요하다

구간 추정은 과거 진척률의 25/75 분위수를 뒤집어 씁니다.

#### 정확도 검증 (2025년 11월, 실제 32.99억)

| 시점 | 예측 | 오차 |
|------|------|------|
| 10일 | 34.87억 | 5.70% |
| 15일 | 36.07억 | 9.36% |
| 18일 | 34.89억 | 5.78% |
| 22일 | 34.68억 | 5.14% |
| 25일 | 33.22억 | **0.72%** |

월이 진행될수록 실제값에 수렴합니다. 15일에 오차가 커진 건 그 달에 심어둔
이상 구간(11/17 인력 이탈) 직전이라 진척이 과대평가된 것으로, 의도한 동작입니다.

표본이 부족하면 숫자를 단정적으로 보여주지 않고 **신뢰도 라벨**을 붙입니다
(`높음` ≥ 12개월 / `보통` ≥ 6개월 / `참고용(표본 부족)`).

### 4. 합성 데이터도 설계가 필요하다

난수만 뿌리면 대시보드가 아무 의미가 없습니다. 실제 데이터에 있는 구조를 넣었습니다.

- **요일 효과** — 월요일 1.18 ↔ 일요일 0.28
- **연간 계절성** — 3월·9월 성수기, 1월·8월 비수기 (sin 주기)
- **성장 추세** — 2년에 걸쳐 콜 물량 +18%
- **지점 편차** — 12개 지점의 전환력·객단가가 각각 다름
- **채널·상담유형별 전환 보정** — 지인소개는 예약 전환 +14%p, 재방문 +18%p
- **이상 구간 5개** — 탐지 로직 검증용 정답 레이블

생성 결과: 상담 **65,674건** / 계약 13,670건 (계약률 20.8%) / 2024-01-01 ~ 2025-12-31

## 실행

```bash
# 1) 백엔드
python -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt

python backend/scripts/generate_data.py        # 합성 데이터 생성 (~5초)
cd backend && uvicorn app.main:app --reload --port 8000

# 2) 프론트엔드 (새 터미널)
cd frontend && npm install && npm run dev
```

→ http://localhost:5173 · API 문서 http://localhost:8000/docs

## API

| 엔드포인트 | 설명 |
|-----------|------|
| `GET /api/meta` | 데이터 범위·차원 목록 |
| `GET /api/funnel/snapshot` | 일간 퍼널 + 최근 N주 같은 요일 비교 |
| `GET /api/funnel/period` | 기간 합계 퍼널 |
| `GET /api/funnel/series` | 일자별 시계열 |
| `GET /api/drilldown` | 차원별 드릴다운 (`branch`/`region`/`channel`/`category`) |
| `GET /api/drilldown/cancel-reasons` | 이탈 사유 분포 (단계별 이탈 지점 포함) |
| `GET /api/anomaly` | 특정 일자 이상 판정 |
| `GET /api/anomaly/scan` | 구간 이상 일자 스캔 |
| `GET /api/forecast/revenue` | 당월 매출 예측 + 과거 실적 |

## 한계와 다음 단계

- **이상 탐지가 룰 기반입니다.** 표본이 쌓이면 계절성까지 분해하는 STL 잔차 기반이나
  Prophet 계열로 옮기는 게 다음 단계입니다. 지금은 설명 가능성을 우선했습니다.
- **예측이 월 단위 총액만 냅니다.** 지점별·상담유형별로 쪼개려면 계층 예측
  (hierarchical forecasting)에서 상위-하위 합계를 맞추는 처리가 추가로 필요합니다.
- **SQLite를 씁니다.** 단일 파일로 재현 가능한 게 우선이었습니다. 데이터가 커지면
  집계 쿼리를 사전 계산 테이블로 빼는 작업이 먼저입니다.
